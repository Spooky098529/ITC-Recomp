# Known functions: the frame driver and the app's scene

Two objects the framework makes once at boot (`Framework::Init`,
[`framework.md`](framework.md)), which carry the frame from the main
thread to the render thread. The frame driver is the game's object that
drives each frame across its render thread (the game's own name for it
isn't known; mapped as "the renderer" and renamed 2026-11-13), not our
Vulkan renderer (`../native-renderer.md`):

- **The frame driver** (400 bytes, `FrameDriver::Create` keeps frame driver + 20 at
  framework + 76; its constructor `FrameDriver::Init`). It is a game
  `Thread` (+0 to +16, the class below: the render thread runs its slot
  1, `FrameDriver::ThreadLoop`, on hardware thread 1 at normal priority)
  with an interface at +20 (vtable `0x82000D6C`: 0 a thunk to the
  deleting destructor, 1 `FrameDriver::AddListener`, 2
  `FrameDriver::RemoveListener`, 3 `FrameDriver::GetVideoOutput`), its own
  listener map at +28 (a `HandlerMap`, keys in order) with a request
  vector at +40 (+44 first, +48 last, +52 end), the video output at +64
  ([`video-output.md`](video-output.md)), the device while a frame is
  drawn at +384 and two events at +388 (the frame's start) and +392 (the
  frame done). On the run loop it adds tick handler 2
  (`FrameDriver::StartFrame`: signals +388), tick handler 16
  (`FrameDriver::WaitForFrame`: waits for +392, then applies the listener
  requests) and the listener for event 6 (its shutdown). On its own map
  it adds its listeners 3 (the resolve into the front buffer) and 5
  (`FrameDriver::Present`). The render thread's frame,
  `FrameDriver::DrawFrame`, locks the device and calls every listener in
  key order with r4 = frame driver + 20 and r5 = the device: 1
  `Scene::Draw`, 3, 5.
- **The app's scene** (80 bytes, `Scene::Create`, at framework + 80;
  vtable `0x82000F3C`: 0 the deleting destructor, 1 the command list's
  getter, 2 the render queue's). Not the car scene `[0x826C2E44]`
  ([`scene.md`](scene.md)). +4 the framework's +8 interface, +8 the
  command list ([`command-list.md`](command-list.md)), +64 the render
  queue ([`device-shaders.md`](device-shaders.md)). Its constructor,
  under the device lock, sizes the list (512,000 slots), sets the queue
  up, sets up the graphics library's draw globals (the work memory, 77
  vertex declarations, default constants) and the primitive vertex
  declaration, and publishes the list and queue in globals the
  recorders read (`0x8296B918`, `0x8296B91C`, `0x82970BD4`,
  `0x82970BD8`, `0x826D83D0`). It adds `Scene::Draw` as the frame driver's
  listener 1, `Scene::Update` as tick handler 18 (the command list and
  the queue flipped once a tick) and the listener for event 5 (its
  shutdown).

The listeners for events 5 and 6, which take everything back off when
the event's word is 1, never ran (nothing sends those events in play:
the run loop's slot 7, `sub_8209A008` in `framework.md`, never ran), nor
did the destructors. The game's `Thread` class (vtable `0x8206CB30`)
is shared with the worker pools (`sub_82094F30`, a lead in
`../loops/leads.md`) and the dirty-disc report (`ReportReadError`,
[`files-and-saves.md`](files-and-saves.md)); its kernel wrappers
(`CreateThread`, `SetThreadPriority`, `XSetThreadProcessor`,
`ResumeThread`) are the core's threads, like `CreateThread` with a
processor (`sub_825BA380`, [`app-start-up.md`](app-start-up.md)).

By the graphics call ("native if the renderer needs it, else Dropped",
`../loops/b7-loop.md`'s "Precedent first") the scene's set-up is kept:
our renderer replays the command list and queue, the draw globals are
the constants and declarations the recorders hand it, and the work
memory is what the morphs write. The frame driver's events are
`Event::Create`'s (`video-output.md`), which stays recompiled by the
user's call (2026-10-24: the core's shared sync).

Shared, in other files, which keep their rows: `FrameDriver::Create` and
`Scene::Create` (`framework.md`); `CommandList::CommandList`, `Init`,
`Flip` and `BeginTick` (`command-list.md`); `RenderQueue::RenderQueue`,

and `functions.md`); `CreateVertexDeclaration` (`app-start-up.md`) and
`Memory::AllocVirtual` and `AllocPhysicalEx` (`shader-objects.md`);
`HandlerMap::HandlerMap`, `Insert`, `RequestVector::PushBack` and
`Clear`, the run loop's `AddTickHandler` and `AddListener`
(`framework.md`); `HandlerMap::ForEach` and `App::ForEachRequest`
(`app-states.md`); `Device::Resolve`'s wait `sub_8229F1B0`
(`command-buffer.md`); the empty destructor `sub_82106540`

the game's functions are in [`functions.md`](functions.md).

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
`itc_recomp/tools/check_function_statuses.py` checks this column, in
every file of the tables, against `src/` (an override marked Native, a
status with no override, an override with no row, a row in two files);
run it after changing either, on any branch.
