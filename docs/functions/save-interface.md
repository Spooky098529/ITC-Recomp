# Known functions: the save system's interface

The game's code between its front end and the save devices: the
interface over the app at `[0x826BDC90]` (`8209FFB8`-`820A0620`, beside
`Archive::AssetSize`), the save devices' small vtable slots it reaches
(the request setters and the slot getters), the users' two slots it
reaches for the save slot of a controller, and the front end's save
layer above it (`8228F6B0`-`82290640`): the save buffers at
`[0x828161F0]`, the game data's save and load (`SystemData.bin`, 129,400
bytes, the player's save data), and the replays' list, save, load and
delete (`rep_...` files, 1,231,088 bytes), with the play time update
the save writes first. B4 made what's under it native at the Xbox
boundary (`files-and-saves.md`, `src/saves/`: the device selector,
content create, enumerate, open and close answered from `saves/`), and
B5 the users (`system-services.md`); the save devices' update is
there, their creation in `framework.md` and their constructor here
(since 2026-11-13: it makes the storage devices' notification listener,
which B5 dropped), the save data in memory in
`save-data.md`. Nothing else here calls an Xbox service itself: the
interface only sets the slots' request words and reads their answers
(the device, its free bytes, the enumerated saves), which
`SaveDevices::Update` (`system-services.md`) turns into the `SaveSlot`
steps; the one kernel-side call is `XUserGetName` (`sub_8228F7D0`,
never ran, already ours).

How the interface finds its objects (read from the code and the image,
2026-10-28): the app's start-up (`sub_82106548`) calls
`SaveInterface::Init` (`sub_8209FFB8`) with app + 16, the app's
interface with vtable `0x82000E38`, which keeps it at `0x826BDC90`. That
interface's slot +12 (`sub_820943B0`) gives the save devices: the word
at this + 8 (app + 24, the framework's +36 interface, vtable
`0x82000AFC`), its slot +40 (`sub_82090788`, `framework.md`: the word at
framework + 124). Its slot +8 (`sub_820943C8`, `system-services.md`)
gives the users the same way: slot +36 of the +36 interface
(`sub_82493700`: framework + 128). The save devices' vtable is
`0x82002198` (the constructor `sub_820A6160`, here since 2026-11-13): 0 `sub_820A6110`
(the destructor, over `sub_820A56E8`; never ran), 1 to 8 `sub_820A5750`
to `sub_820A5808`, 9 and 10 folded getters (`sub_824936E8`,
`sub_8248F030`), 11 `sub_820A5848`, 12 `sub_820A5860`, 13 `sub_820A55A8`
(`files-and-saves.md`), 14 `sub_820A5580`, 15 `sub_820A52E0`, 16
`sub_820A53E8`, 17 `sub_820A54E8`. The users' vtable is `0x82000FA0`
(slot 1 `sub_82490B08`, slot 2 `sub_820996D8`). Each wrapper here takes
a slot index (one 1,000-byte save slot a signed-in user, from the save
devices' +44) and the front end gets it from a player through the
controller table (`0x826BABA4`, `Players::ResetControllers` in
`save-data.md`) and `SaveSlots::OfController` (`sub_8228F780`).

The slot's state (+988, slot 7), the handler `SaveDevices::Update`
runs for it every frame (read from the handlers, 2026-11-13; the rows
below): 0 no user, 1 no device, 2 a save, load or delete failed (+992
says which, until +980 acknowledges it), 3 ready, 4 the device selector,
5 the enumeration, 6 the enumerated saves' check, 7 the save, 8 the
load, 9 the delete. (Read from the front end on 2026-10-28 as "2 no
device"; the handlers say a device-less slot sits in 1, and 2 is the
failure state.) Its request words, each set to 1 by a
setter here and summed by `SaveSlot::Pending` (slot 8): +960
the device selector (`SaveSlot::WaitDeviceSelector` clears it and sets
+964), +964 the enumeration (also set when a save ends), +968
the save, +972 the load, +976 the delete, +980 the failure's
acknowledgment (`sub_820A5860`, never ran; state 2 clears it with +992
and goes back to 3). The save, load
and delete setters copy the display name (+504), the file name (+760)
and the path (+802, `TXR360:\TXR_DATA_1`) into the slot first, and do
nothing (0) unless the slot is ready (3).

The slot handlers (mapped 2026-11-13 by the B7 loop from the lead the
save devices' constructor added; read in full in `generated/`): the
ten words at the save devices' +76 to +112 (`SaveDevices::SaveDevices`
stores them), each called by `SaveDevices::Update`
(`system-services.md`, every frame) with r3 = the save devices (the
owner) and r4 = the slot, returning the slot's next state (+988). States
0 to 3 only look at the request words and the device; 5, 6, 7, 8 and 9
are machines over a sub-step word (+96 the enumeration's, +128 and
+132 the check's step and item, +948 the save's, load's and delete's)
that start their B4 step (`files-and-saves.md`: the device selector,
`SaveSlot::Enumerate`, `OpenItem`, `Create`, `WriteFile`, `ReadFile`,
`SetThumbnail`, `Delete`, `XContentClose`, all answered at once from
`saves/`) and then poll its overlapped without waiting. 6 to 9 run one
slot at a time: the first claims the owner's +72 (0 free), the others
stay in their state until it's given back. The save's, load's and
delete's error words: +952 (0 none, 1 failed, 2 no room), +992 the
failure state's reason (2 the save failed, 3 no room for it, 4 the
load failed, 5 the delete failed). States 4 (`SaveSlot::WaitDeviceSelector`),
7 (`SaveSlot::SaveStep`) and 8 (`SaveSlot::LoadStep`) keep their rows
in `files-and-saves.md` (B4's), read in full there now, with the
callees only the save and load steps call (the waits, rows here). The
handlers' polls reach the kernel only through `XGetOverlappedResult`
(`sub_82295C98`) and `GetOverlappedResult` (`sub_82295F20`), both in
`files-and-saves.md`, always with wait 0 from here: B4's steps mark every
overlapped done at once, so they read the overlapped and never reach
their wait (`WaitForSingleObject` `sub_822970A0`, `video-output.md`,
kept recompiled by the user's call, 2026-10-24: the core's shared sync).

user's call 2026-10-29), never taken from these callers. `CloseHandle`
(`sub_82294E20`, `functions.md`, a ready group itself) is called by the
close's wait only for a file or event handle, which B4's steps never
make (+496 = -1, +492 = 0). Shared, with rows elsewhere: the
framework's +56 interface's slot 1 (`sub_820908D8`, `framework.md`,
seen, a ready group: the device list `SaveDevices::Update` reads the

Made native by the B7 loop on 2026-10-28 (`--native_save_interface`,
plain C++ in `src/save_interface/`, adapters in
`src/hooks/save_interface.cpp`, harness `save_interface`): every row in
play. The wrappers reach the save devices and the users through vtables:
the plain C++ checks each target first (reads only) and hands back to the
original where one isn't this file's (never in play: the harness checks
the game's vtables hold them). The save devices' slots, the users' and
the app's getters stay adapters (reached through vtables), as do
`SaveInterface::Init` (the app's start-up is recompiled), the save
buffers' Create and Destroy, `SaveSlots::RequestDevice`, `State`,
`Device` and `Pending`, `PlayTime::Update` and the play time's
`sub_821109B8` (front-end callers), `GameData::Save` (GetLocalTime takes
`ctx`) and `Replays::BuildList` (a replay's parse, never in play, is the
original's through the guest). What the originals leave in their frames
as data (GameData::Save's name and time, PlayTime::Update's out,
Replays::Sort's copy, BuildList's count) is written there too; register
saves and callees' back chains aren't. The harness never touches the live
objects: its interface, save devices, slots, users, save data and save
buffers are copies in harness memory, the globals pointed at them while a
case runs.

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
