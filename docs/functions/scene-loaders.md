# Known functions: the scene's loading objects

The first set of the scene's object pools (`[0x826C2E40]`, 140 bytes;
`../known-data.md`) and the loading objects it holds, one class a pool:
the car model (pool 0), the car parts (1), the cockpit body (2), the
interior (3), pool 4's single model, the wheels (5) and the traffic body
(6). This file holds their lifetimes: the set made (`ScenePools::MakeA`)
and filled (`ScenePools::CreateA`: each object allocated, constructed and
linked into its pool's list as a `PoolNode`), each class's constructor,
reset, release (`ScenePools::ReleaseA` picks it by the pool) and
destructors, the embedded loads each class keeps (load slots, a skeleton,
XPRs, texture providers and part models; `CarModelLoads` and the like),
the load callbacks of the cockpit body, the interior and the traffic body
(the node file's skeleton bound, posed and searched by node name), their
small queries (loaded yet, a part by its kind, the walks over the arrived
parts), and the name and point helpers the car code shares: an XPR's
records found by name (`XPR::FindByName`, a case-insensitive match with
`*` wildcards) and a model's named node turned into a point record
(`ModelPoint::Find`, 12 callers among the second set's objects). The
loaders that start the loads (`CarModel::LoadExterior`,
`CarInterior::LoadSetCBody`, `CarInterior::Load`, the wheels' and the
decals') and the car model's own load callbacks and release are in
`car-models.md`; the parts', pool 4's and the traffic body's loaders in
`scene-models.md`; the second set, which claims these objects, in
`scene-models.md` and `vehicle-accessors.md`. Shared, with their rows
elsewhere: `CarModel::Release` (`sub_820D4508`), `LoadSlot::Reset` and
`ReleaseBuffer` (`sub_820D0730`, `sub_820D0758`), `sub_820C3F50` (the
deferred release) and `Texture::Create` in `car-models.md`; `Skeleton::`
(`model-animation.md`); `Model::`, `XPR::`, `TextureProvider::`,
`sub_82599A20`, `sub_82599AF0`, `sub_82599C58` and the part model's
`sub_820CE928`, `sub_820CE990`, `sub_820CE9C8`, `sub_820CE9F8`
(`models.md`); the record resets (`CarRecord::Reset`, `sub_820D45B0`,
`sub_820D3558`, `sub_820D3840`, `sub_820D34B8`, `sub_820D3900`,
`sub_820D34E0`, `sub_820D3B38`) and `sub_820F0E50` (`scene-models.md`);
`List::At` (`vehicle-accessors.md`); `VirtualAlloc` (`heap.md`);
`memcpy`, `sprintf`,
`toupper` (`c-runtime.md`); `DataFile::GetEntry`
(`files-and-saves.md`); the matrix functions (`matrix-math.md`). Not
here (leads in `../loops/leads.md`): the part models' material passes the
walks call (`sub_820D0EA8`, `sub_820D2EA8` and their neighbors at
`820D0D50`-`820D3728`), the second set's users of `ModelPoint::Find`, the
accessories' release below `sub_820F0A90` (`sub_820F0988`), the traffic
body's second texture (`sub_820ED6D0`, already in the graphics resources'
lead), the texture providers' slot 2 (`sub_82594328`, in the course
scenery's lead) and the first set's teardown (`sub_820C4C80`,
`sub_820C3DA0`, in the scene update's lead). Mapped 2026-10-28 by the B7
loop from the lead "the car code's skeletons"; every row below was read
in `generated/` (offsets are the object's own unless said).

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
`itc_recomp/tools/check_function_statuses.py` checks this column, in
every file of the tables, against `src/` (an override marked Native, a
status with no override, an override with no row, a row in two files);
run it after changing either, on any branch.
