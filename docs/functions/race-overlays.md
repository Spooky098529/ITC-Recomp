# Known functions: race overlays

The race overlays: the effects drawn around each car in a race (the
trails behind its wheels, tire smoke, sparks, two other particle
effects, light glows, and the marker above opponents), about `82121000`
to `8212EE00` in `default.xex`, with their manager around `8215DE80` to
`8215E6C0` and the single-sprite classes at `8211E8A8` to `8211F430`.
The race scene's owner keeps a list of 25 overlay pointers at owner +
9608 (`RaceOverlays::`); one entry a car (up to 7, made by
`sub_8215E208`) is a `CarOverlays` object (848 bytes, vtable
`0x82008524`), which owns 38 child overlays of seven classes (4 trails,
4 smoke emitters, 4 light sprites, 8 spark emitters, 4 of particle
effect B, the marker, 4 of particle effect C, 9 car-model sprites). Each
`CarOverlays` holds up to 25 views (16-byte objects: a vehicle, its
scene model and a viewport), set up by `sub_8215E2E0` per car and per
player. Every tick the manager (`sub_8215DEA0`, overridden: updates on
logic passes only) calls each `CarOverlays`' update (vtable slot 4,
`sub_82126220`), which reads its car's wheels, body and model points and
feeds the children (emitting particles, adding trail points, placing
sprites), then calls each child's own update (slot 4: ageing and fading
its particles); then each `CarOverlays`' recording (slot 5,
`sub_82122958`) calls each child's recording (slot 7, with the camera
pass index), which fills sprite lists and records them. The recordings
and the sprite recorders are in [`sprites.md`](sprites.md) (shared:
`sub_82129A08`, `sub_8212ACF0`, `sub_8212BB20`, `sub_8212C6D0`,
`sub_8212DFB8`, `sub_8212CE40`, `sub_8211EC18`, `sub_82123300`,
`sub_82126630`, `sub_821266C8`); how the overlays are drawn every frame and blended is
"Race overlays" and "World-space sprites" in
`../frame-interpolation.md`. Layouts are in `../known-data.md` ("car
overlays" and the rows after it). Mapped by the B7 loop
(`../loops/b7-loop.md`), 2026-10-22, from the generated code only (no
runs): call counts aren't known; vtable slots are inferred from the
constructors' vtable addresses and the callers' offsets (the vtables
themselves, in `.rdata`, weren't read). Shared callees in other files:
`sub_820AB560` (Wrapped), `sub_82597118`
and `Vehicle::GetSpeedKmh` (`sub_820C0128`, Overridden) in
[`functions.md`](functions.md); `sub_825A7410` (`memcpy`),
`sin`, `cos`, `acos` and the stack probe `sub_825A9934` in
[`c-runtime.md`](c-runtime.md); `Archive::Load` (`sub_8209DE48`) in
[`files-and-saves.md`](files-and-saves.md); `sub_82596E68` and `sub_82596F68` (a texture set made and
loaded), `sub_82108860` (a texture set released), `sub_82295398` and `sub_82295330` (probably
VirtualAlloc and VirtualFree), `sub_825A6880` (probably operator new) and
`sub_825A70E8` (probably operator delete) are leads in
`../loops/leads.md`. The overlays allocate guest memory (their objects,
views and texture tables through `sub_82295398`, the texture set through
`sub_825A6880`): making the creation side native waits on the user's
call on the guest heap; the update side doesn't allocate. Made native
from the bottom up by the B7 loop (2026-10-22): plain C++ in
`itc_recomp/src/race_overlays/`, adapters in `src/hooks/race_overlays.cpp`
behind `--native_race_overlays`, harness `race_overlays`. Learned there:
the translated code's `lfs`/`stfs` pairs keep a float's bits (signaling
NaNs too: the float-to-double-and-back folds away), so native copies move
words; the slot 4 updates (`Marker::Update`, `Trail::Update`) are reached
only through the vtable, so their adapters stay until `CarOverlays::Update`
is native and calls them some other way. The second pass (2026-10-22)
added the car-model sprites' kind and table entry, `ParticlesB::Emit`,
`ParticlesC::Emit` and `Trail::AddPoint`. Learned there: the translated vector code (`AddPoint`'s
vector lengths and cross product) switches flush-to-zero on around each
vector instruction, so the native version does the same around its SSE
(denormal squared lengths count as 0.0); with NaNs among the inputs, the
NaNs that come out differ in sign and payload between builds of the same
operations, as SSE passes on the first operand's NaN and the compiler
picks the operand order and even rewrote the Newton step (seen in the
disassembly), so the harness keeps those cases in an "(expected to
differ)" group. `Trail::AddPoint` wasn't called in 35-second attract
races (the trails are probably skid marks, and the AI cars didn't skid). The third pass (2026-10-22) added the model points' checks and
positions (`OverlayView::HasPoint` and `PointPosition` with the scene
model's and its parts' functions behind them, reached only from there, so
Native without adapters), `Sparks::UpdateStreak`, `Sparks::Emit` and
`CarOverlays::EmitSmoke` with `Smoke::Emit`. Learned there: which NaN a
vector addition passes on when both lanes are NaNs depends on the order the
compiler gave `addps` its operands, in the translated code too (seen in the
disassembly: the translated `Smoke::Emit` keeps the PowerPC's first
operand first, the two sparks functions have theirs swapped), so
`Smoke::Emit`'s native drift keeps the first operand's NaN explicitly and
the sparks use a plain `addps`, which matches them as built; a rebuild
that changes the translated code's choice would show in those harnesses as
NaN-only differences. `Sparks::Emit` wasn't called in 25-second attract
races (no scraping). The fourth pass (2026-10-22) added `OverlayView::SpeedKmh`,
calling `Vehicle::GetSpeedKmh`'s plain C++ (now declared in
`src/hooks/vehicle.h`). Learned there: a tail call leaves the callee's
arguments in its registers (the vehicle in r3), which the harness compares,
so the adapter returns r3 as the original does. The same pass then took the set-up's
constructors, clears and bindings, the children's resets and
constructors (none allocates; the allocations stay in their recompiled
callers), `Smoke::InRegion` and `Sparks::Update`. Learned there: stvx
stores to the 16-byte-aligned address below its operand, so the identity
rows of `Sprite::ResetStyle2` and `SmokeEmitter::Reset` are stored there;
a float the translated code keeps as a double across a branch (the first
+104 store of `Sparks::Update`) comes back with a signaling NaN quieted,
while a plain load and store keeps its bits; and `Sparks::Update`'s
additions keep the destination's NaN (seen in the disassembly), so the
native version picks it explicitly. The fifth pass (2026-10-22) added the
children's updates `Smoke::Update`, `ParticlesB::Update` and
`ParticlesC::Update` (their adapters stay: slot 4) and
`RaceOverlays::SlotOf`; the adapters of `SmokeEmitter::Reset`,
`Smoke::InRegion` and `ParticlesB::ResetEntry` went. Learned there: a `tw`
trap in the translated code only logs (`ppc_trap` type 0 warns and runs on,
the division by 0 giving 0), so with a capacity of 0 the originals run their
index on past the entries (into whatever follows, whose counts then drive
the inner loops): the harnesses keep the counts small there, and don't try
heads below 0, where the originals reset entries over the object's own
capacity and table pointer. Which NaN an addition or product keeps is the
x86 destination's, which the compiler picks per lane (seen in the
disassembly): `Smoke::Update`'s particle additions keep the position's for x
and the velocity's for y and z, `ParticlesB::Update`'s the velocity's for all
three, `ParticlesC::Update`'s pull product the difference's; products the
translated code computes in doubles from a loaded single come back with a
signaling NaN quieted. `sub_8215E150` (the Update handler's thunk) was left
for `RaceOverlays::Run`: alone it would only be an adapter passing r3 + 9,608
to that function's `ctx` override, and its harness would have to run that
override (camera passes saved, the blend handler set) outside the game's
update.

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
`itc_recomp/tools/check_function_statuses.py` checks this column, in
every file of the tables, against `src/` (an override marked Native, a
status with no override, an override with no row, a row in two files);
run it after changing either, on any branch.
