# Known functions: the type 6 and 7 modes

The front-end game modes of **type 6 and type 7** (`Mode::Create` and
the modes' constructors are in [`game-modes.md`](game-modes.md), the
constructors of their screen blocks in
[`screen-constructors.md`](screen-constructors.md)): two hubs over the
player's own car on the stand, probably. Each mode's slot 0
(`Type6Mode::Init`, `Type7Mode::Init`) starts the UI movies, loads
string files 0 and 1, makes the stand scene for one car
(`StandScene::Create`: the viewports, the car scene and three garage
stages, the stand of [`front-end-car-draw.md`](front-end-car-draw.md)),
`VirtualAlloc`s its screen block (91,272 or 71,292 bytes, at the mode's
+848) and builds it, runs each member's Init (their transitions, through
`StateMachine::Add`), adds the members' machines to the mode's
dispatcher, shows the loading screen and fades in. Its delegate then
waits for every screen's movies (`WaitForLoads`), starts the menu music
(bank 1's cue 2) and posts the "loaded" message (34 in type 6, 28 in
type 7), which opens the first screen; from there the next-mode query
(`NextMode`) runs the machines until one reaches state 10, then the mode
leaves (`Leaving`: every machine to state 6) and tears down (`TearDown`:
the stand scene's teardown, the music stopped) and answers the next
mode: 1 (the race) when the list screen ended in state 11, else 4 (back
to the type 4 front end). Slot 1 (`StandMode::Release`, shared) frees
the stand, the block, the strings and the UI movies.

The first screen (`Type6Screen0`, `Type7Screen0`) is a menu over the
mode's car (a global garage car filled once from player 0's save data:
the selected garage car, or a stock car 0 with an empty garage),
which the stand shows. Type 6's menu has five items (strings 109, 120,
110, 113, 114): the list screen (message 14; in state 11 it sets the
race data from its picks and the mode answers the race, so probably the
race or course pick), the node screen (16; type 6 only), the panel
screen (18; a panel menu over the car), the options (26) and quitting
(two confirms, then the save screen, message 29); button 163 opens the
car's power graph screen (21). Type 7's has four (109, 110, 113, 114):
its list screen (13; a 15-item list with one or two color bits an item),
the panel screen (15), the options (23) and quitting (one confirm, no
save screen); its power graph is message 18. Type 7's message ids are
mostly one lower than type 6's. Each block also holds a yes/no dialog
(`Type6Dialog`, `Type7Dialog`: UI movies 16 to 19) and the options'
controller pages (`ControllerOptions`, drawn inside the options' movie
7, shown only for the options' context 4; not seen in play). Which of
the game's modes the two are by name isn't settled (the string table
wasn't read): both are races with the player's own car, type 6 the
larger (its node screen and the save on quitting). The list, node and
panel screens' handlers, the power graph screen's, the options' and the
save screen's are not mapped here: their Inits are (the transitions
listed, the handlers named by address), the handlers are leads in
`../loops/leads.md`; none of the list or node screens' open, Draw or
Update handlers ran in the coverage sessions (`../coverage.md`).

Messages (type 6 / type 7) and states as the screens use them: 0 Update
and 1 Draw; the loaded message 34 / 28; leave 4 / 3; states 0 enter, 1
open the movie, 2 wait for it, 9 wait for the mode, 4 show, 5 shown, 8
suspended, 7 leaving, 6 done, 10 leave the mode. Names are ours. The
transitions were worked out by replaying the Inits' stores and copies,
then checked against the code; `StateMachine::Add` replaces a key
already there, so for a key registered twice the last registration
wins. The modes', the screens' and the stand's fields are in
`../known-data.md` ("type 6 screens", "type 7 screens", "type 6 and 7
modes", "the type 6 and 7 cars", "stand scene holder", "garage stage",
"garage camera"). Read by the B7 loop's mapping agent, 2026-11-07, from
the two leads "the type 6 mode's slot 0" and "the type 7 mode's slot 0"
and the car scene owners' lead (`sub_82180B00`, `sub_82179AE8`,
`sub_82180AA0`).

For a migration (all in the rows): the only kernel calls are
`VirtualAlloc` and `VirtualFree` (the allocation layer's; zeroed pages
are relied on, as the original gets them); the garage camera's presets
arrive through an archive callback on the loader thread
(`GarageCamera::OnPresetsLoaded`, as the archive's other callbacks);
handlers call their pages and steps through tables (in the image for
`Type6Screen0`, built at run time with guard words at `0x82815E20` and
`0x82815E3C` for `Type7Screen0`, on the stack for the dialogs and the
controller pages); messages are posted straight into the dispatcher's
ring with no overflow check; stack bytes land in live state (the
answer's bytes +91257 to +91259, `Type6Mode::Init` and `Leaving`;
precedent: memory leftovers copied as the original leaves them); the
mode's delegate is rewritten while it runs (`ModeDelegate::Invoke`,
`boot-mode.md`); `UiMovie::SetText` calls leave r7 to r10 unset
(precedent, 2026-10-30: pass 0); car objects are built in 4 KB stack
frames.

The migration (B7 loop, 2026-11-07, `--native_type67_modes`, harness
`type67_modes`, `src/type67_modes/`): the 16 state machine Inits replay
step tables decoded from the generated code by a script that followed
their registers and ran their six-word copy loops (`init_tables.h`); the
handlers that allocate or free run over the allocation layer only (the
adapters fall back to the originals off it, or where a block isn't its
pages); `UiMovies::IsLoaded` on an id not in the movie table reads the
word at `0x826C5CDC` as the movie (the harness plants a movie there for
its cases, and 0 for `UiMovies::Delete`'s callers, which would otherwise
unload what it finds); the pages' handlers the Draw handlers call and
`GameMessages::Dispatch` stay guest calls. The third (2026-11-07) kept those rules:
the dialogs' pages and Updates, the first screens' helpers, OpenMovie,
SetUpCar and OnDialogClosed, `ControllerOptions::Update` and the modes'
`WaitForLoads` call `Menu::Step`, `Menu::Pressed`, `MenuSound::Play`,
`Sound::Play`, `ScreenFades::FadeOut`, `GarageStage::SetDrawWord` and the
UI movies' node and text setters through their plain C++, and make guest
calls to the overrides of the steps and pages in tables, `UiMovie::Run`,
`FinishAll`, `LoadingScreen::Run` and `Finish`, `GarageStage::MakeModel`,
`Command` and `Draw`, `GarageCar::Reset` and `Type6Screen0::ConfirmAgain`
(whose adapter therefore stays). Their harness worlds keep those callees
cheap: the stage's model claimed (MakeModel does nothing) and its garage
camera not set up (Command 14 and Draw only store or return), the loading
screen's movie a harness movie whose update is recorded, the controller
pages' steps 0 and 3 with their started word set (they answer 1). Where a
recompiled caller's callees would run recompiled with the flag off and
leave register saves the native side doesn't, the cases run the original
with the flag on (`OnDialogClosed`) or the steps recompiled on both sides
(the dialogs' Updates).

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).
