# Known functions: C runtime

The game's statically linked C runtime and math library (Microsoft's, for
the Xbox 360), as seen in play: the math functions, the floating-point
helpers they share, the string, memory and character helpers, the
number parsing and formatting (`sprintf` and its float conversion), and
the small pure pieces of its start-up. It sits at about `825A6880` to
`825B9A60` in `default.xex`; below it (`8259C000` to `825A6800`) is the
UI movie library (`UiMovie::` in [`functions.md`](functions.md), a lead
in `../loops/leads.md`), above it the kernel import thunks and threads.
Mapped by the B7 loop (`../loops/b7-loop.md`) from the stack probe
(`sub_825A9934`) and `acos` (`sub_825A8170`), which block the sprite
overlays in [`sprites.md`](sprites.md). The C runtime's globals are in
`../known-data.md`.

Not here: the heap (`sub_825A6880`, `sub_825A6940`, `sub_825A70E8`,
`sub_825A71C0`, and under them `sub_825A9A90` and `sub_825A9B58`, the
allocation and free over HeapAlloc and HeapFree, `sub_825AC320` calloc,
`sub_825AEBC8` and `sub_825AED30`; their rows are in `heap.md`, over
the native allocation layer since 2026-10-22, `docs/native-memory.md`), and what
calls kernel imports, which goes with the core: the locks
(`sub_825AA1A8` and `sub_825AA1B0` over `sub_825B3430` and `sub_825B32D0`,
critical sections), `atexit` (`sub_825A7068`, 124 static set-ups
register their clean-up with it, with `sub_825A6F60`, `sub_825A7044`,
`sub_825A6F00`; it locks and grows its table on the heap), the per-thread
data (`sub_825AA580` `_getptd`, `sub_825AA4C0`, `sub_825AA400`,
`sub_825AA708`, `sub_825AA670`, `sub_825B3650`: TLS), the lock and stream
tables' set-up (`sub_825B31D8`, `sub_825B35A0`, `sub_825AD4D0`,
`sub_825B4668`), and `_controlfp` (`sub_825AB400`,
KeEnableFpuExceptions). Shared with other files: `sub_82106540` (an
empty function, in [`audio.md`](audio.md)), called by `_init_pointers`.
The game's own wrappers that jump here (`sub_82295D48` to `wcscpy`) stay
in their files.

Matching the translated code: native math must give the same doubles,
bit for bit, as the translated PowerPC code, NaNs and denormals
included. What that takes, from the generated code:

- `fmadd`, `fmsub`, `fnmsub` and `fnmadd` are translated as `std::fma`
  (one rounding): native code calls `std::fma` at the same steps, and
  builds with no other contraction (`-ffp-contract=off`, no fast math),
  as a separate multiply and add round twice.
- The polynomials' coefficients are tables of doubles (and some floats)
  in guest memory (`../known-data.md`): native code uses the same values
  (read once from the guest, or copied as hex constants), in the same
  order of operations.
- `fsqrt` and `fdiv` are correctly rounded on both sides (`sqrt`, `/`).
  `fsel` is `a >= 0.0 ? b : c` (a NaN picks c); `fcmpu` comparisons with a
  NaN are all false.
- `fctid` (`sin`, `cos`, `pow`'s integer test) rounds by the host's
  rounding mode (`cvtsd2si`), `fctidz` truncates; a NaN gives
  `0x8000000000000000`, and too large saturates.
- The translated scalar code turns the host's flush-to-zero off before
  floating-point work (`ctx.fpscr.disableFlushMode()`); vector code turns
  it on. Native code called from translated code must run with it off
  too, or denormals differ.
- `mffs` and `mtfsf` read and write only the rounding mode
  (`FPSCRRegister::loadFromHost`, `storeFromGuest` in the SDK's
  `rex/ppc/context.h`): `_ctrlfp` (`sub_825B0B80`) sees no exception bits,
  so the error paths that test them (`_except1` and the like) never ran.
  `_ctrlfp`'s adapter does the same three steps in the same order
  (`loadFromHost`, flush-to-zero off, `storeFromGuest`), so the host's
  MXCSR and the context's copy of it end the same; its harness sets each
  rounding mode first and puts the thread's MXCSR back after every call.
  Native code under `-ffp-model=strict` follows the host's rounding mode
  (`rint`'s two additions do, in all four).
- `sub_825A9DB0` converts a 64-bit integer to a double by truncating, not
  rounding.
- NaN signs: LLVM treats a NaN's sign as free, so the translated code's
  NaN results don't always follow the PowerPC steps: `fmul` by 2.0 then
  `fneg` (`asin`, `acos`) is folded into a multiply by -2.0, which keeps
  the default NaN's sign (x86's `sqrtsd` of a negative gives
  `0xFFF8000000000000`). The native math (`src/c_runtime/math.cpp`) builds
  with `-ffp-model=strict` (no such rewrites of its own: with the default
  model, -O3 moved a negation into an addition and flipped the sign of
  `asin` of a negative NaN) and writes the translated code's folds where
  the harness shows them (`Sqrt(z) * -2.0`); `fsqrt` is the SSE2
  instruction, not libm's `sqrt` (which gives `0x7FF8...` under the
  strict model).
- Harnesses: a recompiled function that tail-calls another overridden one
  runs the override (`acos`'s recompiled version runs the kernel's native
  one), so the kernel's own cases are the check. The same holds for a
  caller that calls them: `pow`'s recompiled version calls the native
  `log`, `_decomp`, `_get_exp`, `_set_exp`, `copysign` and the integer
  test, so its harness checks `pow`'s own steps, and each helper's cases
  compare it against its recompiled version. Inside native code the
  helpers are plain calls (`c_runtime::Decomp`...), so a counter at their
  adapters sees only their other callers.
- `tan`, `ldexp` and `_clearfp` call `_ctrlfp`: their adapters make its
  calls on the context themselves (`CtrlFp` in `src/hooks/math.cpp`, the
  same three steps), so the MXCSR and the context's copy of it end as the
  original leaves them; `tan`'s work runs between the two calls, in the
  nearest mode they set. Where the originals go to their `_except` and
  `_except1` paths (a NaN, out of range), the adapters run the original
  instead, and the harnesses leave those inputs out: those paths reach the
  C runtime's exception handling (`sub_825B0068`, which calls `_clearfp`
  and `_controlfp`), never seen in play.
- `fctiwz` (`pow`) is `cvttsd2si` on 32 bits, a NaN giving `INT32_MIN` and
  2^31 - 1 and above `INT32_MAX`; `stfiwx` stores its low word.
- The helpers that take a double's bits (`copysign`, `_set_exp`,
  `_get_exp`, `_decomp`, `pow`'s integer test) go through the stack
  (`stfd`, then halfword and word loads); native code works on
  `std::bit_cast` bits. Several store f1 (and f2) in the caller's linkage
  area (r1 + 16 and + 24); no caller reads those words back (checked over
  every caller in `generated/`), so the native versions don't store them.

The error paths (`_errno` `sub_825A81E0` and `_invalid_parameter`
`sub_825AFCC8`, called with EINVAL 22 or ERANGE 34; the math functions'
`_except1`, `sub_825B0968` and the like) never ran in play: native code
for a function keeps them on the recompiled path behind its flag, or
ports them, and the row says which.

The string and character helpers (`src/c_runtime/strings.cpp`) work on
guest memory through `src/guest.h`, element by element in the original's
order, so overlapping copies and unaligned or page-crossing strings come
out the same; where a function returns a pointer or adds to its argument,
the adapter keeps the register's high word as the original leaves it.
Where the original reaches `_errno` and `_invalid_parameter` (`strcpy_s`,
`_strnicmp`, `strtoxl`), the native code decides first, writing nothing,
and the adapter runs the recompiled function instead. The character type
tables (`../known-data.md`) and the current locale's pointer are read from
guest memory on every call, not copied: the locale is the game's to change.

The long double conversions under `atof` and `%f` (`_ld12tod`, `___dtold`)
and `printf`'s `write_char` (`src/c_runtime/format.cpp`) follow the
original's integer steps; `_ld12tod`'s format descriptor is constant data,
copied. `write_char` leaves no room left (`_flsbuf`, a file write) to the
recompiled function, as the error paths above. `write_multi_char`, the wide `write_char` and
`_putwc_nolock` (the same file) do the same for `_flsbuf`, `_flswbuf`, the
console (stdout and stderr), file streams and `_errno`, deciding before they
write anything; where a buffer's bytes would land on the stream's own words
or the count, `write_multi_char` can't decide first and runs the original.

The start-up's pieces (`src/c_runtime/start_up.cpp`: the float conversion
table, `_init_pointers`' setters, `__initmbctable` and `setSBCS`) run once
at boot and store into live globals; their harness saves each global and
puts it back around every call. Where a native version calls another
(`sub_825A6E48` the table's fill, `__initmbctable` `setSBCS`), it calls the
plain C++, so the callee's adapter is only reached from the fallback.

`memcpy` (`sub_825A7410`) copies with the host's memcpy only where that
gives the original's bytes: ranges that don't share memory. Guest views
share host memory (`map_info` in the SDK's `src/system/xmemory.cpp`):
`0x80000000` and `0x90000000` both show the xex, `0x7F000000`,
`0xA0000000`, `0xC0000000` and `0xE0000000` (offset by 4 KB) the physical
memory, so overlap is checked in the memory behind the views, and a range
crossing into another view goes to the original. Its callers' registers
were checked by a script over every call site (what each reads before
setting it, up to the first branch).
The parsing under `atof` (`src/c_runtime/parse.cpp`: `_atof_l`, `_fltin2`,
`__strgtold12_l` and `__mtold12`) follows the original's steps on its own
copy of `__strgtold12_l`'s stack frame (big-endian bytes at the same
offsets), so its 96-bit products, carries and rounding come out the same;
only the end pointer and the result are written to guest memory. Its
callers read nothing but r3 or f1 after each (checked over every call
site, up to the first branch).
`$I10_OUTPUT` and `_fltout2`, the digits under `%f` (the same file), share
that multiplication by powers of ten, with `$I10_OUTPUT`'s own frame
offsets; their writes into their callers' frames (arguments saved there)
aren't made, as no caller reads them.
The %f text above them (`_cftof_l`, `_fptostr`, `_cftof2_l`, the same
file) is laid out in the guest buffer by `memmove`s, `memset` and byte
stores; the native versions work on a `GuestText` (bytes read from the
guest when first needed, writes kept in host memory) and write the bytes
set only at the end, so the adapters can still run the original after the
work is done: where the writes reach the physical views (`memmove`'s copies
down go through `memcpy`, whose copies there are recorded for the
renderer's mirrors), cross two views, or share memory with what's read
(the result, the digits, the locale's decimal point). `_cfltcvt_l` stays a
dispatch in its adapter: only %f is native, %e, %g and %a stay recompiled
(never seen in play).

`memmove` (`sub_825AA840`) uses the same rule for its backward copy: where
the ranges share memory in one view, the guest's order is the host's, so the
host's memmove gives the original's bytes; through two views it can't be
told, and the original runs. Its test is signed (`cmpw`), but no view
crosses `0x80000000`, so within one view that's the address order.
`memcpy_s` (`sub_825A7270`) calls `memcpy`'s override rather than copying
itself, so the renderer's mirrors still see its copies.

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
`itc_recomp/tools/check_function_statuses.py` checks this column, in
every file of the tables, against `src/` (an override marked Native, a
status with no override, an override with no row, a row in two files);
run it after changing either, on any branch.
