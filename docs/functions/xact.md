# Known functions: XACT

XACT, the Xbox 360's sound library, linked into the game (recompiled
guest code; see "How the game's audio works" in `../native-audio.md`).
The game's sound manager and its thin wrapper over XACT are in
[`sound-cues.md`](sound-cues.md), which lists the vtable slots the
wrapper calls; this file is the library below them, as far as the
wrapper reaches it in play. XACT here is the XACT3-era runtime with the
360's interfaces (XACT2-like slot orders) and XACT2-era big-endian files
(`.xsb` "KBDS" sound banks, `.xwb` "DNBW" wave banks, used in place in
memory). Its objects, reached through vtables (the wrapper never calls
these functions directly):

- **The engine** (`XACTEngine`, 196 bytes, made once by
  `XACT3CreateEngine`, kept at `[0x82971478]`): vtable `0x82075360`
  (+0 AddRef, +4 Release, +8 Initialize, +12 ShutDown, +16 DoWork,
  +20 CreateSoundBank, +24 CreateInMemoryWaveBank, +28
  CreateStreamingWaveBank, +32/+36 probably Register/UnRegisterNotification,
  +40 GetCategory, +44 Stop, +48 SetVolume, +52 Pause, +56 to +64
  probably the global variables'). It holds the global settings
  (`XACTGlobalSettings`, from `TXR_XACT.xgs`: categories, variables),
  the lists of cues, sound banks and wave banks, the notification
  registrations, a lock (+144) and the renderer (+12).
- **The renderer** (`XACTRenderer`, 448 bytes, vtable `0x820753F0`):
  XACT's side of XAudio: starts XAudio, registers the engine's audio
  callback, makes the voices and starts the deferred ones.
- **Sound banks** (`XACTSoundBank`, 268 bytes, vtable `0x82075A90`:
  +4 Prepare, +16 Destroy, +20 GetState) over a `.xsb` file; **wave
  banks** (`XACTWaveBank`, 292 bytes, vtable `0x82075AE8`: +0 Destroy)
  over a `.xwb` file (the game's: 349 PCM and 41 XMA entries, 44.1 kHz).
- **Cues** (`XACTCue`, 352 bytes, vtable `0x82075908`: +0 Play, +4 Stop,
  +8 GetState, +12 Destroy, +48 Pause, +60 GetProperties), each playing
  one **sound** (`XACTSound`, 128 or 140 bytes) of tracks; volume fades
  through 24-byte **faders** (no fade ran in play).

The per-frame work comes in two halves: `XACTEngine::DoWork`
(`sub_825C1990`, on the game's thread from `AudioEngine::DoWork`: each
cue's slot +76 update, each wave bank's slot +52, deferred deletes)
and the engine's audio callback (`sub_825C0248`, which XAudio calls on
its own thread, probably every processing pass: each cue's slot +72
fade step and the sounds' audio update, each wave bank's slot +56),
both under the engine's lock. A translation needs both entry points (or
one that does both).

Where XACT reaches below itself (the boundary a translation must
replace with our own audio output; how is the user's call):

- **XAudio** (`8245xxxx`, not mapped; a lead): at start-up the
  renderer (`sub_825C2BB0`) calls `XAudioInitialize` (`sub_8245A760`),
  registers the audio callback (`sub_8245A5E8`, through `sub_8245AB60`:
  `KeRaiseIrqlToDpcLevel`, `KeAcquireSpinLockAtRaisedIrql`) and reads
  the output's channel count (`sub_8245A568`, `sub_8245A3B8`); the
  renderer's slot +20 (`sub_825C3048`) starts the deferred voices
  (`sub_8245A6E8`). The voices themselves are a 24-byte class
  (vtable `0x82075B98`, `825C9B60`-`825CA448`, a lead), driven from the
  tracks and waves at `825D0000`-`825D5000` (a lead), each method one
  XAudio call: create source voice `sub_8245A768`, state
  `sub_82459FA0`, volume `sub_8245A2C8`, pitch `sub_8245A340`, submit
  packet `sub_8245A108` (pointers into the in-memory wave bank: XMA
  with its seek table, or PCM), start (deferred or now) `sub_8245A168`,
  stop `sub_8245A1B0`, flush `sub_8245A208`, release `sub_82459E18`
  (all "probably"). XMA is decoded below XAudio (B2: ours, FFmpeg's
  `xma2`, `../native-audio.md`).
- **The kernel**: `RtlEnterCriticalSection`, `RtlLeaveCriticalSection`
  (the engine's lock), `RtlInitializeCriticalSection`; the clock
  (`sub_825BFE28`: `QueryPerformanceCounter` `sub_825BA0C8` over the
  frequency at `[0x82971480]`, or the tick count `sub_822956F0`); the
  thread id (`sub_825B9A60`).
- **Memory**: `XMemAlloc` and `XMemFree` (`heap.md`, on the native
  allocation layer), `memset`, `memcpy` (`c-runtime.md`).

Shared with other files, which keep their rows: `XACT3CreateEngine`
(`sub_825BF5C8`), the engine's constructor `sub_825C09A8` and
`XAudioInitialize` (`sub_8245A760`) in `sound-cues.md`; `sub_825C8388`
(returns 0) and `sub_825C8390` (returns 1), small functions the linker
folded with game code, in `vehicle-accessors.md`; `sub_82106540` (an
empty function) in `audio.md`; `XMemAlloc`, `XMemFree`, `operator new`,
`operator delete` in `heap.md`; `memset`, `memcpy` in `c-runtime.md`;
`QueryPerformanceCounter`, `QueryPerformanceFrequency` and
`sub_825B9A60` in `functions.md`. `sub_825CED88` is also called by the
movie player and `sub_8259A140`. The rest of XACT seen in play (the
tracks, events and waves at `825D0000`-`825D5000`, the voice class, the
global settings' and the cue's never-mapped slots, the engine's
remaining methods) is in `../loops/leads.md`. Objects, fields, file
layouts and tables are in `../known-data.md`. The rows were drafted by
the B7 loop's mapping agent (2026-10-23) from the generated code and
the game's own `.xsb`/`.xwb` files; nothing here ran differently.

Making it native: translating XACT to native C++ is expected (the
user's call, 2026-10-23: no host library plays XACT's data), from the
leaves up, as for the game's code; the top of it waits on the
boundary above.

Status:

- **Native**: plain C++ in `itc_recomp/src/` that doesn't use the
  PowerPC context (`ctx`): normal arguments and host structs (it may
  still read and write guest memory through `src/guest.h` while
  recompiled code shares the data). The game reaches it without `ctx`,
  from native or overridden callers, and the recompiled original is no
  longer called (except behind a fallback flag or to check against it).
  No `REX_FUNC` override of it exists, not even an adapter kept only for
  a harness (that's Overridden until the adapter goes).
  The end state for every function.
- **Overridden**: an `extern "C" REX_FUNC(sub_XXXXXXXX)` override in
  `itc_recomp/src/` (or a macro defining one) does the work instead of
  the original: a thin adapter in front of native code, or a body that
  still uses `ctx` (calling guest code, reading registers). It may call
  the original when its flag is off, or to check itself against it.
- **Wrapped**: an override that does something of its own (skipping
  render-only passes, logging, timing) and still calls the original
  (`__imp__sub_XXXXXXXX`) for the work.
- **Dropped**: its work isn't needed on PC (hardware set-up, kernel calls
  the SDK already stubbed), so it no longer runs: an override in
  `itc_recomp/src/` replaces it with nothing (or a fixed return value), or
  its callers, made native, leave the call out (no override then; the row
  says which caller). Logs, a harness or the renderer's frame dumps have
  shown that nothing reads what it did. The original is no longer called,
  except behind a fallback flag while the drop is being checked. A
  function the game never calls in the first place isn't Dropped: its
  status stays blank and its row says it's never called.
- **Merged**: its work is done inside a native caller's plain C++ (a
  few lines only that caller needs), so it has no function or override of
  its own in `itc_recomp/src/`. The row names the caller(s) and the
  harness that covers the work. The original is no longer called, except
  behind the caller's fallback flag.
- **Patched**: the generated code was edited in place (search for
  `PATCH:`).

A function usually moves from recompiled or Wrapped to Overridden to
Native as the `ctx` edge moves up through its callers, or straight to
Dropped when its work isn't needed.
`itc_recomp/tools/check_function_statuses.py` checks this column, in
every file of the tables, against `src/` (an override marked Native, a
status with no override, an override with no row, a row in two files);
run it after changing either, on any branch.
